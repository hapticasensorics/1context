1Context Wiki Productionization Plan

Make the wiki dead simple to operate: plain Markdown as source of truth, deterministic static rendering, atomic publication, and a small stable API for the rest of the system. Keep it powerful by treating profiles, projects, topics, and agent context as typed wiki pages rather than a separate memory product.

Decision

Use one boring wiki pipeline

The durable source lives as user-owned Markdown under ~/1Context/wiki. The renderer writes rebuildable outputs into a staging directory. Memory core validates wiki semantics. The app mechanically gates and atomically publishes a safe static bundle into ~/Library/Application Support/1Context/wiki-site/current. Caddy serves only the current bundle. The Swift API serves only small dynamic state and search over the published content index.

Simple

Markdown files, predictable folders, no database required for page source, no render-on-request, no Python web server in the product path.

Reliable

Render to staging, validate semantically, gate mechanically, publish atomically, keep the last good site, and make refresh failure visible without blanking the browser.

Powerful

Profiles, projects, topics, people, organizations, preferences, and agent startup context are all pages with frontmatter, links, talk folders, evidence, and stable routes.

Current State

Area State Gap
Repo wiki source Public-safe defaults live in runtime/1Context/user-wiki. These are templates and first-run source seeds, not installed personal content.
Renderer The first-class wiki-engine/ renders Markdown, talk folders, routes, and indexes. Swift calls the bundled renderer and preserves the last good site on render failure.
Routes and indexes The renderer writes route manifests, content indexes, markdown twins, and page results. Configured pages use user source first and fall back to templates when source is absent.
Installed local web Swift/Caddy serves wiki-site/current and dynamic /api/wiki/*. The daemon installs runtime defaults, renders, gates, and atomically publishes.
User wiki source ~/1Context is the intended user-owned content root. The installed app does not yet create or publish a user wiki workspace there.

The rest of the system should consume wiki data through routes, manifests, content indexes, and explicit source paths. It should not scrape random generated HTML, and it should not mutate generated files.

Markdown Contract

A page is just Markdown with frontmatter. Profiles are pages too. That keeps the system understandable and lets people repair memory with a text editor.

# Your Context

## Working Style

Durable facts go here only when they are explicit or evidence-backed.

Page kinds

Kind Where it lives Use
rolling_memory_surface for-you.md Current open loops, fresh observations, and memory queue.
operator_profile your-context.md Human profile, preferences, working style, standing requests.
project 20-project/.../source/*.md Active, paused, completed, or archived project pages.
topic 30-topics/.../source/*.md Concepts, tools, systems, organizations, people, and domain ideas.
agent_profile 30-topics/.../source/agents/*.md Stable instructions for a recurring agent role.

Rules for Markdown files

  • Source pages are human-editable and durable. Generated pages are rebuildable.
  • Every durable claim should be explicit, evidence-backed, or marked as a hypothesis.
  • Internal links use stable routes such as /your-context or /topics/tool-slug.
  • Talk folders keep proposals, disagreements, and curation decisions out of the main article.
  • Private content stays private by default. Public or shareable output must be an explicit audience tier.

Validation Boundary

Swift has no semantic understanding of whether agents wrote a good page, finished a thought, or made the right curation decision. That is intentional. Swift's job is to keep the wiki up.

Layer Responsible For Must Not Do
Agents and memory jobs Propose, discuss, edit, cite evidence, and improve pages over time. Assume their output is automatically safe to publish.
Python memory core Semantic wiki validation: family manifests, frontmatter, routes, links, privacy tiers, render manifests, content indexes, and stats. Serve browser traffic in the public app or mutate app-owned current output in place.
Swift static bundle gate Mechanical uptime checks: required files exist, JSON parses, paths stay inside the bundle, symlinks are rejected, private/internal/talk/source artifacts are excluded, and atomic swap can complete. Read source Markdown, judge page meaning, repair agent prose, or duplicate family/frontmatter logic.
Caddy Serve wiki-site/current and reverse-proxy the small dynamic API. Render, validate, or know about memory jobs.

Hard rule

A broken or weird semantic wiki can fail to publish, but it must not take down the last good wiki. The app should prefer an old current bundle over a fresh bundle that fails mechanical checks.

Agent Contract

Agents should not think about publishing. Their contract is to read the wiki, propose or apply source edits when authorized, leave reasoning in talk folders, and cite evidence. Memory core renders and validates. Swift keeps the served wiki up. 

Agent verbs:
  read wiki
  propose or update source
  leave reasoning in talk
  cite evidence
  stop

Agent non-goals:
  publish bundles
  write wiki-site/current
  repair app-owned local web state
  decide whether a bundle is safe to serve

Agent-facing status

Condition What Agents See What Agents Do
Normal healthy wiki Wiki status: current site is healthy. Read the served URL and content index. Edit source only when the role allows it.
Source has unpublished edits Source status: unpublished edits pending validation. Use source pages as latest editing truth; use served URL as last reader preview.
Semantic validation failed Repair needed: broken link /projects/foo in topics.md. Run the targeted repair task and leave reasoning in the relevant talk folder.
Mechanical publish gate failed Current site stayed on last good publish. Usually no action. The runtime or app maintainer handles bundle-gate failures.

Status files

The runtime should reduce publish state into small files that can be summarized into startup context. Agents should not parse renderer logs or infer publish state from directory contents. 

~/Library/Application Support/1Context/wiki-build/
  last-success.json              # last successful semantic render + publish handoff
  last-failure.json              # last failed semantic render or validation
  current-source-state.json      # source hash, unpublished-change count, latest edit time

Publish Flow

sequenceDiagram
  participant D as Daemon
  participant M as Memory core
  participant S as Source wiki
  participant R as Renderer
  participant V as Semantic Validator
  participant P as Python Publisher
  participant G as Swift Bundle Gate
  participant C as Caddy

  D->>M: request publish or refresh
  M->>S: ensure scaffolding
  M->>R: render families into staging
  R-->>M: render manifests and outputs
  M->>V: validate routes, links, privacy, checksums
  V-->>M: pass or fail report
  alt pass
    M->>P: build static bundle
    P->>P: write publish-manifest.json
    P->>G: hand off candidate bundle
    G->>G: mechanical safe-to-serve checks
    G->>G: atomic swap next to current
    C-->>D: serves new current site
  else fail
    M->>P: record last-failure.json
    C-->>D: keep last good current site
  end

Publication invariants

  • wiki-site/current is always servable if any successful publish has ever happened.
  • Refresh never deletes current before next has passed semantic validation and mechanical bundle checks.
  • Swift performs only mechanical bundle checks; Python owns semantic wiki validation.
  • Agents never publish; they repair source when given a targeted semantic validation failure.
  • Failure records are machine-readable and visible through diagnostics.
  • Caddy never reads source Markdown or staging directories.
  • The app can fall back to the bundled shell only when there is no last successful render.

Implementation Plan

1. Restore the design surface

  • Add this productionization plan and keep it linked from docs/README.md.
  • Write a shorter Markdown contract later if release tooling needs a non-HTML spec.
  • Document which folders are durable, rebuildable, app-owned, and user-owned.

2. Create user wiki bootstrap

  • Add a command that initializes ~/1Context/wiki from seed family templates.
  • Copy only source, family manifests, group manifests, and templates. Do not copy generated files.
  • Make wiki ensure idempotent against the user wiki root.

3. Add publish bundle support

  • Add memory-core/src/onectx/wiki/publish.py.
  • Render into wiki-build/staging/<render-id>.
  • Copy only public generated HTML, Markdown twins, assets, and JSON indexes into a bundle.
  • Write publish-manifest.json with source hashes, render id, generated time, and validation status.

4. Make local web consume published bundles

  • Add WikiStaticBundleGate.swift for mechanical bundle checks and atomic directory swaps between next, current, and previous.
  • Change daemon refresh from placeholder-only to: use last good bundle, publish fresh bundle when available, otherwise seed placeholder.
  • Keep the static fallback shell in release/memory-runtime/source/wiki-site.

5. Expose the right context to agents

  • Point agent startup context at the local wiki URL and published content-index.json.
  • Summarize publish state into one or two lines from last-success.json, last-failure.json, and current-source-state.json.
  • Give agents targeted repair tasks for semantic validation failures; do not expose mechanical bundle-gate work as normal agent work.
  • Use Your Context as the primary human profile page.
  • Use typed topic pages for people, organizations, tools, and agent profiles.
  • Keep publishing out of agent prompts: agents read, edit or propose source, write talk notes, cite evidence, and stop.

Milestones

  1. Spec closed: this HTML plan is checked in, linked, and used as the target for implementation.
  2. Bootstrap works: a fresh user install can create ~/1Context/wiki with the four seed families and no generated content committed as source.
  3. Publish works: one command renders, validates, writes a bundle, and atomically updates wiki-site/current.
  4. App refresh works: the menu/daemon refresh path publishes or keeps last-good output instead of writing only the placeholder shell.
  5. Agent context works: agents can read the wiki URL, content index, Your Context, Projects, Topics, and concise wiki status without learning how publication works.

Risks To Keep Small

Too many roots

Keep durable source under ~/1Context/wiki and served output under app support. Do not add another canonical wiki location.

Generated files becoming truth

Generated HTML, Markdown twins, manifests, and indexes are useful, but rebuildable. Source Markdown and evidence receipts carry truth.

Silent privacy leaks

The publisher must reject private/internal outputs in user-facing bundles unless an explicit audience tier asks for them.
