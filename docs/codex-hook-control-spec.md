# Codex Hook Control And Mail Wakeup Spec

- Status: target contract for Codex-backed autonomous mail wakeups
- Last updated: 2026-05-25
- Sources: [Codex Hooks](https://developers.openai.com/codex/hooks),
  [Codex App Server](https://developers.openai.com/codex/app-server),
  [Codex Config Reference](https://developers.openai.com/codex/config-reference),
  [Codex Sandboxing](https://developers.openai.com/codex/concepts/sandboxing),
  [Codex Permissions](https://developers.openai.com/codex/permissions),
  [Codex Rules](https://developers.openai.com/codex/rules)

This document defines how 1Context should use Codex control surfaces and hook
surfaces to make agent mail work without a human manually waking every agent.
The concrete implementation boundary for the app-server client, hook manager,
wake dispatcher, injection bridge, and event mirror is
[1Context Codex Adapter Spec](1context-codex-adapter-spec.md).

It is not a claim about hidden Codex internals. For a production client, the
wire-level source of truth is the schema generated by the installed Codex
version:

```bash
codex app-server generate-ts --out ./schemas
codex app-server generate-json-schema --out ./schemas
```

The product contract below is stable at the 1Context layer even if the adapter
has to follow Codex version-specific schema details.

## Core Model

1Context has a durable mail kernel and a Codex-facing control plane:

```text
durable mail kernel
  messages / deliveries / claims / notifications / governance ledgers
        |
        v
Codex mail control plane
  wake dispatcher / hook bridge / event mirror / content injector / policy engine
        |
        v
Codex app-server
  thread/resume / turn/start / turn/steer / thread/inject_items / item events
        |
        v
Codex agent
  inbox -> open -> claim -> act -> mark/defer/reply -> ack
```

Agents talk to each other by sending mail. The system turns eligible deliveries
into runtime hooks for live recipients.

```text
agent A calls wiki.mail.send
-> durable message accepted
-> per-recipient delivery rows created
-> notification rows created for matching non-retired agents
-> dispatcher steers active agents or resumes/starts inactive agents
-> agent B opens, claims, acts, marks, and acks
```

The hook is a wakeup hint. The mail delivery is the work truth.

The doctrine:

```text
mail          = durable work truth
notification  = wakeup hint
steering      = live control signal
injection     = model-visible content delivery
hooks         = lifecycle enforcement and observation
events        = runtime evidence
```

The Codex control plane is an adapter layer, not a second mail system. It may
wake, steer, inject, guard, mirror, and report, but it must not invent delivery
truth or silently mutate message truth.

```ts
type CodexMailControlPlane = {
  wakeDispatcher: "turn/steer | turn/start | thread/resume orchestration";
  hookBridge: "Codex hooks -> MailControlEvent";
  contentInjector: "wiki.mail.open content_delivery -> thread/inject_items";
  eventMirror: "Codex runtime events -> mail evidence";
  policyEngine: "mail state machine + Codex approval/sandbox posture";
  supervisor: "lease, retry, suppress, dead-letter, recovery";
};
```

## Control Taxonomy

| Class | Examples | Strength | Use In 1Context |
| --- | --- | --- | --- |
| Durable controls | mail acceptance, delivery state, claims, marks, ledgers | High | Source of work truth |
| Hard runtime controls | sandbox, approval denial, permission profile, `PreToolUse` deny | High | Safety and irreversible actions |
| Approval controls | `PermissionRequest`, user approval, `auto_review`, app tool approval modes | Medium-high | Policy and human/policy gates |
| Soft steering | `turn/steer`, `thread/inject_items`, hook-added context | Medium-low | Wakeups, nudges, corrections |
| Observation controls | item events, deltas, hook logs, notification attempts | Indirect | Audit, replay, debugging |

Invariant:

```text
Soft steering may tell an agent what to look at.
Durable mail tells an agent what work exists.
Hard controls decide what the agent is allowed to do.
```

## App-Server Lifecycle Controls

The Codex app-server is a JSON-RPC control plane for rich clients. A 1Context
adapter should treat the generated schema for the installed Codex version as
the exact wire contract.

| Control | Kind | 1Context Use |
| --- | --- | --- |
| `initialize` / `initialized` | connection lifecycle | Required before any thread/turn operations. |
| `thread/start` | lifecycle | Start a new live agent thread. |
| `thread/resume` | lifecycle | Reattach to an existing agent transport. |
| `thread/fork` | lifecycle | Branch agent work when policy allows. |
| `turn/start` | lifecycle | Begin a new explicit agent turn. |
| `turn/steer` | soft steering | Wake or redirect an active in-flight turn. |
| `turn/interrupt` | lifecycle stop | Cancel active work when mail/policy requires it. |
| `thread/inject_items` | history injection | Add provenance-pinned context without starting a user turn. |
| `thread/compact/start` | lifecycle | Compact long-running threads. |
| `thread/rollback` | lifecycle | Rewind thread state under explicit operator/supervisor policy. |
| `thread/read`, `thread/list` | observation | Inspect persisted thread status without waking an agent. |
| `thread/loaded/list` | observation | Discover loaded threads eligible for live steering. |
| `thread/name/set`, `thread/goal/set` | metadata | Name or goal live agent threads, not mail deliveries. |
| `review/start` | workflow | Request a Codex review pass; not a mail notification primitive. |
| event stream | observation | Observe item starts/completions, deltas, approvals, errors. |

### Turn Steering

`turn/steer` is the best Codex primitive for a live mail notification when a
recipient thread is already active.

1Context steering payloads must:

- include `agent_id`, `notification_id`, `delivery_id`, `message_id`, recipient,
  subject, kind, priority, timestamps, and optional page reference
- target the active in-flight turn according to the installed Codex schema; if
  the schema exposes `expectedTurnId`, pass the current active turn id and fail
  closed on mismatch
- tell the agent which `toolset-mail` operations to call next
- omit the full message body
- be idempotent for the same notification id
- fail closed if the target thread/turn no longer matches

`turn/steer` is not a delivery state transition. It is accepted or rejected by
Codex transport, then the 1Context notification ledger records the dispatch
attempt. The delivery remains unread until the recipient opens or marks it.

### Thread Injection

`thread/inject_items` is not a wakeup by itself. Use it for provenance-pinned
context such as memory packets, summaries, or prior evidence that should become
model-visible history.

Do not use `thread/inject_items` as a replacement for mail delivery state. The
exception is deliberately narrow: after `wiki.mail.open` authorizes a specific
delivery, the Codex host should use `thread/inject_items` as the content
delivery lane for that opened body. The durable truth still remains the mail
message, delivery row, notification row, and open/claim/mark ledgers.

For opened mail, the refined flow is:

```text
agent calls wiki.mail.open(delivery_id)
-> mail core checks lease, visibility, and delivery state
-> tool returns bodyless summary plus content_delivery
-> Codex host adapter executes thread/inject_items
-> adapter writes a MailInjectionReceipt / MailControlEvent
-> model sees the body as injected message content
```

The actual app-server call should live in the host adapter or an event
middleware queue, not inside a hook script that recursively talks to the same
app-server transport. Hooks may emit or enqueue the request, but reentrancy
should stay boring.

```ts
type MailInjectionReceipt = {
  injection_id: string;
  delivery_id: string;
  message_id: string;
  agent_id: string;
  thread_id: string;
  body_sha256: string;
  item_count: number;
  app_server_method: "thread/inject_items";
  app_server_result: "ok" | "failed";
  created_at: string;
};
```

### Inactive Or Missing Threads

The dispatcher chooses a deterministic wake strategy from the agent directory
and app-server thread status:

```ts
type CodexWakeStrategy =
  | "steer_active_turn"
  | "start_wake_turn"
  | "resume_then_start_wake_turn"
  | "start_new_thread_then_register"
  | "poll_only";
```

| Recipient State | Preferred Action | Mail Rule |
| --- | --- | --- |
| active in-flight turn with known turn id | `turn/steer(expectedTurnId)` | Send a small envelope, then wait for open/ack/claim. |
| loaded thread, no active turn | `thread/inject_items` with notification envelope, then `turn/start` with tiny wake prompt | Envelope only, no body. |
| persisted resumable thread | `thread/resume`, let `SessionStart` add pending digest, then `turn/start` | Record resume and dispatch attempts separately. |
| archived thread | `thread/unarchive`, then resume/start if policy allows | Record unarchive separately from mail delivery. |
| missing thread | start new Codex thread and register a new transport if supervisor policy allows | Leave old delivery unread until a valid agent opens it. |
| known agent, expired lease | supervisor may resume/start; agent self-poll still fails until heartbeat | Durable notification remains pending. |
| unknown address | route failure/dead letter | Do not invent a Codex thread. |
| retired agent | reroute if role/list policy allows | Otherwise dead-letter or leave assigned by policy. |

`thread/inject_items` can prepare notification envelope context for a resumed
agent before the wake turn, but that envelope is a doorbell, not the package.
It does not replace the mail notification or delivery row.

When the supervisor wakes an inactive agent, it should renew the agent lease or
make `wiki.agent.heartbeat` the first step in the resumed turn before asking
the agent to claim or mark mail. Durable notification visibility and agent
self-mutation are intentionally separate.

Wake envelopes must be small:

```json
{
  "kind": "mail.control.notification_wakeup",
  "source": "1context.mail",
  "notification_id": "notif_...",
  "agent_id": "agent_codex_...",
  "delivery_id": "delivery_...",
  "message_id": "mailmsg_...",
  "mailbox": "role://topics.curator",
  "priority": "normal",
  "body_included": false,
  "instruction": "Call wiki.agent.inbox, open this delivery, then claim or defer before acting."
}
```

## Execution And Policy Controls

The mail system must not confuse a wakeup with permission. A notification can
tell an agent what to inspect; sandbox, approvals, command rules, app/tool
policy, and host policy decide what it can do.

### Sandbox And Approval Policy

| Control | Values Or Shape | 1Context Mail Policy |
| --- | --- | --- |
| `sandbox_mode` | `read-only`, `workspace-write`, `danger-full-access` | Notifications must not request broader sandboxing. |
| `approval_policy` | `untrusted`, `on-request`, `never`, granular object | Mail tools should work under the current policy; risky actions ask normally. |
| `approvals_reviewer` | `user`, `auto_review` | Reviewer choice is not a sandbox expansion. |
| permission profile | filesystem/network read/write/deny profiles | Use for command execution boundaries, not for message routing. |
| command rules | prefix allow/prompt/forbidden | Protect shell actions around mail/wiki files. |
| `request_permissions` | turn/session-scoped extra grants | A mail notification must never smuggle a permission request. |

1Context should treat these as host/runtime configuration, not message content.
Mail metadata can record the current policy for audit, but agents cannot alter
policy by sending mail.

### Command And Host Execution Surfaces

The pasted control-plane report correctly separates normal sandboxed command
execution from sharper host controls. The adapter should preserve that split.

| Surface | Boundary | 1Context Rule |
| --- | --- | --- |
| `command/exec` | server sandbox | Safe default for product-owned probes when needed. |
| `process/*` | experimental, outside normal sandbox | Do not expose to normal agent mail decisions. |
| `thread/shellCommand` | user-initiated, unsandboxed full-access shell | Never use as an automatic mail notification action. |
| shell environment policy | subprocess environment filtering | Keep secrets out of hook and mail-tool environments. |

If mail work needs a filesystem or shell action, the agent should use normal
tool approval paths. The notification payload should contain a delivery id and
instructions to inspect, not an executable command to run blindly.

### App, Skill, Plugin, And MCP Controls

Codex exposes tools through skills, apps/connectors, plugins, and MCP. These
are not governed solely by shell sandboxing.

| Surface | Useful Controls | Mail-System Use |
| --- | --- | --- |
| skills | `skills/list`, skill enable/disable | Teach agent workflow; do not rely on skills for authorization. |
| apps/connectors | app enabled flags, destructive/open-world flags, per-tool approval mode | Keep open-world/destructive tools explicit. |
| MCP | server enabled state, enabled/disabled tools, approval modes, OAuth/auth status | Good home for `toolset-mail` and `toolset-wiki` once stable. |
| plugins | bundled skills, apps, MCP, hooks | Package toolsets and managed hooks later. |

The agent-facing public surface should stay small: `toolset-mail` and
`toolset-wiki`. App-server, MCP, plugin, and hook wiring are implementation
details behind the gateway.

### Admin And Managed Controls

Managed config can force or restrict hooks, approval policies, sandbox modes,
web-search modes, and command rules. Requirements are a higher-order policy
layer than user preferences.

1Context mail must obey managed policy even if a message asks otherwise. In
particular:

- managed hooks can be required for safety/audit
- `allow_managed_hooks_only` means user/project/plugin hooks should not be
  assumed to run
- admin command rules can prompt or forbid, and mail must not downgrade them
- project-local hooks/config are unavailable until the project is trusted
- notification delivery should record policy refusal separately from agent
  refusal

## Observation And Event Controls

The event stream is the live evidence channel for Codex work. It is more useful
than final answers when debugging autonomous mail because it includes tool
attempts, approvals, deltas, errors, interruptions, and hook decisions.

Do not conflate the three notification surfaces:

| Surface | Meaning | 1Context Use |
| --- | --- | --- |
| Codex app-server notifications | JSON-RPC events such as thread/item/status changes | Observe runtime behavior and correlate evidence. |
| Codex `notify` config | local command invoked for user-facing notifications | Optional operator UI; not agent mail delivery. |
| 1Context mail notifications | durable outbox rows that may dispatch `turn/steer` | Agent-to-agent wakeup and routing contract. |

For autonomous agent mail, the active push mechanism is the 1Context
notification dispatcher sending Codex steering. Codex's local `notify` setting
can be useful for humans, but it should not be treated as delivery to another
agent.

1Context should retain enough event evidence to answer:

- was the recipient thread loaded?
- was a turn active?
- did `turn/steer` accept the notification?
- did Codex emit an error or interruption?
- did a hook block, rewrite, or add context?
- did a permission request surface, resolve, or get denied?
- did the agent later call `wiki.mail.open`, `wiki.mail.claim`, or
  `wiki.mail.mark`?

This event evidence complements the durable mail ledger. Neither replaces the
other.

### Control Events Ledger

Hook behavior becomes ghost governance unless it leaves evidence. Add a durable
control ledger under the mail/control plane:

```text
context-engine/live/mail/control-events.jsonl
```

The ledger records Codex hooks, app-server observations, host injection
receipts, supervisor decisions, and policy refusals. It does not store full
mail bodies or raw transcripts.

```ts
type MailControlEvent = {
  control_event_id: string;
  created_at: string;

  source: "codex.hook" | "codex.app_server" | "mail.supervisor";
  hook_event_name?:
    | "SessionStart"
    | "UserPromptSubmit"
    | "PreToolUse"
    | "PermissionRequest"
    | "PostToolUse"
    | "Stop"
    | "PreCompact"
    | "PostCompact"
    | "SubagentStart"
    | "SubagentStop";

  codex: {
    session_id?: string;
    thread_id?: string;
    turn_id?: string;
    cwd?: string;
    model?: string;
    permission_mode?: string;
    item_id?: string;
    tool_name?: string;
    tool_use_id?: string;
  };

  agent: {
    agent_id?: string;
    lease_state?: "active" | "stale" | "retired" | "unknown";
    active_delivery_id?: string;
  };

  mail_refs: {
    notification_id?: string;
    message_id?: string;
    delivery_id?: string;
    claim_id?: string;
    proposal_id?: string;
  };

  decision?: {
    behavior:
      | "allow"
      | "deny"
      | "block_prompt"
      | "continue_turn"
      | "inject_context"
      | "record_only"
      | "rewrite_tool_input";
    reason?: string;
  };

  input_sha256?: string;
  output_sha256?: string;
  additional_context_sha256?: string;
};
```

Every hook action that affects authority, wakeup state, injection, completion,
or policy should write one of these records. Message truth remains in message
and delivery ledgers; the control ledger explains how runtime control shaped
the agent.

### App-Server Event Mirror

Codex runtime events should be mirrored into mail evidence when they explain
delivery progress or blockage:

```ts
type CodexEventMirrorRule =
  | "mirror_thread_status"
  | "mirror_item_lifecycle"
  | "mirror_approval_requests"
  | "mirror_command_outputs_as_evidence"
  | "mirror_errors_to_supervisor_mail"
  | "mirror_review_results_to_governance";
```

Examples:

- `thread/status/changed` with `waitingOnApproval` creates an
  `agent.runtime.waiting_on_approval` control event and may send supervisor
  mail.
- completed command/file/review items become `evidence_refs` that can justify
  `wiki.mail.mark(done)`.
- app-server errors create supervisor-visible mail with Codex item/thread refs,
  not copied raw logs.

## Codex Hook Events

Codex lifecycle hooks are scripts loaded from user, project, plugin, or managed
configuration. Command hooks are the supported handler shape today. Matching
hooks from multiple files can all run, and multiple command hooks for one event
may run concurrently.

Non-managed command hooks must be trusted before running. Managed hooks are
trusted by policy and cannot be disabled from normal user hook browsing.

### Hook Discovery And Trust

The hook registry is part of the runtime safety surface. The 1Context adapter
should inspect discovered hooks when the installed Codex app-server schema
exposes hook-listing APIs, and otherwise fall back to generated schema plus
local config inspection.

The desired registry record is:

```ts
type CodexHookRecord = {
  key: string;
  eventName: string;
  handlerType: "command";
  matcher?: string;
  command: string;
  sourcePath?: string;
  timeoutSec?: number;
  statusMessage?: string;
  isManaged: boolean;
  enabled: boolean;
  currentHash?: string;
  trustStatus?: "trusted" | "untrusted" | "changed" | string;
  runnable: boolean;
};
```

Mail correctness depends on this because a missing or untrusted `Stop` hook can
change whether claimed-but-unmarked deliveries are caught before the agent
stops. Treat hook registry drift as an environment status issue, not as mail
delivery failure.

### Source, Handler, And Decision Kinds

Codex hook configuration can come from these source kinds:

| Source Kind | Example | Mail-System Meaning |
| --- | --- | --- |
| user config | `~/.codex/hooks.json`, `~/.codex/config.toml` | Personal defaults and experiments. |
| project config | `<repo>/.codex/hooks.json`, `<repo>/.codex/config.toml` | Repo-local behavior; only safe after project trust. |
| plugin-bundled config | installed Codex plugin | Packaged integration behavior. |
| managed config | admin or product policy | Non-user-disableable control surface. |

Codex currently treats command hooks as the meaningful executable handler kind.
The schema may parse additional handler shapes, but `async`, `prompt`, and
`agent` handlers are not a production dependency for 1Context mail until the
installed Codex schema and docs say they run.

| Handler Kind | Current Role | 1Context Policy |
| --- | --- | --- |
| `command` | Supported hook runner. | Allowed for trusted product and project hooks. |
| `async` | Parsed/skipped today. | Do not rely on it. |
| `prompt` | Parsed/skipped today. | Do not rely on it. |
| `agent` | Parsed/skipped today. | Do not rely on it. |

Hook decisions should be classified before use:

| Decision Kind | Examples | Mail-System Rule |
| --- | --- | --- |
| add context | `additionalContext`, stdout context | Can orient agents, but cannot mutate mail state. |
| block/deny | `decision: block`, `permissionDecision: deny` | Can stop unsafe behavior. |
| allow | `permissionDecision: allow` | Can bypass an approval only where product policy permits. |
| continue work | `continue: false`, stop/compact/subagent stop handling | Can keep work alive to resolve claimed mail. |
| rewrite input | `updatedInput` for supported tools | Must be audited; never rewrite mail body authority. |
| suppress output | `suppressOutput` | Logging/UI concern only, not a durable mail transition. |

### Hook Command Contract

Every command hook receives JSON on stdin. The fields to preserve in mail
evidence are:

| Field | Why It Matters |
| --- | --- |
| `session_id` | Links hook behavior to a Codex session. |
| `turn_id` | Links turn-scoped hooks to the active turn. |
| `transcript_path` | Debug pointer only; not a stable product API. |
| `cwd` | Explains which project/config layer was active. |
| `hook_event_name` | Names the hook event. |
| `model` | Useful audit metadata, not mail routing state. |
| `permission_mode` | Explains current permission posture. |

Event-specific fields should be stored when they affect mail:

| Event | Fields Worth Keeping |
| --- | --- |
| `SessionStart` | `source` |
| `PreToolUse` / `PostToolUse` | `tool_name`, `tool_use_id`, `tool_input`, summarized result/failure |
| `PermissionRequest` | `tool_name`, approval description if present, allow/deny/defer decision |
| `PreCompact` / `PostCompact` | `trigger` |
| `UserPromptSubmit` | prompt hash or redacted prompt summary |
| `SubagentStart` / `SubagentStop` | `agent_id`, `agent_type`, `agent_transcript_path` when present |
| `Stop` | `last_assistant_message` hash or summary, `stop_hook_active` |

Do not copy full prompts, full tool output, mail bodies, or transcript contents
into notification payloads. Store redacted hashes/summaries in evidence and
keep body authority inside the mail store.

### Matcher And Timeout Rules

Hook matchers are regex strings. Empty matcher, omitted matcher, or `*` means
"match all" for events that support matching.

| Event | Matcher Meaning |
| --- | --- |
| `SessionStart` | `startup`, `resume`, `clear`, `compact` |
| `PreToolUse` | tool name; `apply_patch` can also match `Edit` or `Write` |
| `PermissionRequest` | tool name; `apply_patch` can also match `Edit` or `Write` |
| `PostToolUse` | tool name; `apply_patch` can also match `Edit` or `Write` |
| `PreCompact` / `PostCompact` | `manual` or `auto` |
| `SubagentStart` / `SubagentStop` | subagent type |
| `UserPromptSubmit` / `Stop` | matcher ignored |

Command hooks run with the session `cwd`. If a timeout is not configured,
Codex's documented default is long enough that product hooks should still set a
short explicit timeout for mail gates. A stuck mail hook must not freeze a whole
agent system.

| Event | Phase | Matcher | Strength | Mail Relevance |
| --- | --- | --- | --- | --- |
| `SessionStart` | thread/session opens | source: `startup`, `resume`, `clear`, `compact` | soft context | Load mail/toolset orientation for the agent. |
| `UserPromptSubmit` | before prompt enters loop | ignored | prompt gate/context | Detect accidental mail-body paste or unsafe operator prompt. |
| `PreToolUse` | before supported tool call | tool name | hard-ish gate | Block unsafe shell/MCP/tool attempts around mail artifacts. |
| `PermissionRequest` | before approval prompt | tool name | approval gate | Auto-deny/allow known mail-adjacent approval cases. |
| `PostToolUse` | after supported tool output | tool name | result gate/context | Detect failed publish, leaked body, malformed mail result. |
| `PreCompact` | before compaction | `manual` or `auto` | lifecycle | Save mail state hints before compaction. |
| `PostCompact` | after compaction | `manual` or `auto` | lifecycle | Reinject "check inbox before stopping" context if needed. |
| `SubagentStart` | before subagent starts | subagent type | soft context | Give spawned agents mail/toolset rules. |
| `SubagentStop` | when subagent stops | subagent type | continuation gate | Require a subagent to mark/delegate claimed mail. |
| `Stop` | when main turn stops | ignored | continuation gate | Prevent an agent from stopping with claimed mail unresolved. |

### Event Caveats

- `PreToolUse` and `PostToolUse` intercept Bash, `apply_patch`, and MCP tool
  calls, but they are not a complete enforcement boundary for every possible
  Codex surface.
- `PostToolUse` cannot undo side effects that already happened.
- `PermissionRequest` only runs when Codex is about to ask for approval.
- `Stop` and `SubagentStop` continuation decisions keep the agent running; they
  are not "reject final answer forever" mechanisms.
- `SessionStart`, `UserPromptSubmit`, and hook-added context are instructions,
  not policy enforcement.

### Codex Hook Control Plane Matrix

Every Codex hook should preserve the mail boundary, enforce the mail boundary,
or mirror evidence back into the mail/control ledger.

| Codex Surface | Mail Control Use | Strength |
| --- | --- | --- |
| `SessionStart` | identify/heartbeat, load pending digest, restore active delivery context | soft context + runtime bookkeeping |
| `UserPromptSubmit` | detect direct user/controller intent, block retired/stale mutations, add inbox context | prompt gate |
| `PreToolUse` | enforce mail tool order and authority before MCP/shell calls | hard-ish gate |
| `PermissionRequest` | approve/deny escalated governance or broad notification actions | approval gate |
| `PostToolUse` | mirror tool results, enqueue/record injections, create receipts/followups | observation + context |
| `Stop` | prevent claimed work from being abandoned silently | completion gate |
| `PreCompact` | snapshot active mail context before compaction | memory guard |
| `PostCompact` | restore active mail context after compaction | memory repair |
| `SubagentStart` | attach delegation scope and child authority limits | delegation |
| `SubagentStop` | require handoff report, evidence, or reply before child exit | delegation closure |

Recommended hook obligations:

```text
SessionStart:
  recover agent identity from thread_id
  heartbeat if policy allows
  add pending notification digest
  restore active delivery context

UserPromptSubmit:
  add inbox/claim context when prompt references mail work
  block retired/stale/unauthorized mutation attempts
  prevent "mark done" prompts without claim/evidence

PreToolUse:
  enforce mail API order
  deny unauthorized claim/mark/open/send
  require idempotency keys and artifact hashes where policy requires them
  prevent raw-body leakage through tool output

PermissionRequest:
  gate governance, role assignment, training-data admission, external send,
  runtime default changes, and mass notification

PostToolUse:
  mirror tool result to control ledger
  execute or queue thread/inject_items for mail.open content_delivery
  produce injection receipts
  generate supervisor mail on errors

Stop:
  prevent claimed delivery abandonment
  require mark/snooze/reject/reply before final stop
  avoid infinite continuation after one or two guard passes

PreCompact:
  snapshot active mail context

PostCompact:
  restore active mail context as developer context

SubagentStart:
  attach delegation context and child authority limits

SubagentStop:
  require handoff report, evidence, or reply before child exits
```

### Mail Runtime APIs For Hooks

Hooks need a cheap way to recover identity and active work from Codex runtime
metadata. Do not make hook scripts scrape transcripts to discover agent state.

Add an internal API:

```ts
wiki.agent.status_by_thread(thread_id): {
  agent_id?: string;
  lease_state: "active" | "stale" | "retired" | "unknown";
  active_delivery?: DeliverySummary;
  pending_notifications: NotificationSummary[];
};
```

This solves the transport/identity split:

```text
thread_id = Codex transport locator
agent_id  = durable mail identity
```

The agent directory owns the mapping from thread id to agent id, roles,
capabilities, leases, and retirement state. Session hooks may recover and
heartbeat an agent from that mapping, but mail authorization still happens in
the mail core.

### Tool Order State Machine

Mail agents should feel natural to use, but legal next moves must be explicit.

```text
notified
-> inbox_seen
-> opened
-> claimed
-> acting
-> replied | artifact_produced | validation_produced
-> done | snoozed | rejected | dead_letter
-> notification_ack
```

Suggested transition table:

```ts
const allowed = {
  notified: ["inbox_seen", "notification_ack"],
  inbox_seen: ["opened", "snoozed"],
  opened: ["claimed", "snoozed", "rejected"],
  claimed: ["acting", "snoozed", "rejected"],
  acting: ["replied", "artifact_produced", "validation_produced", "snoozed"],
  replied: ["done"],
  artifact_produced: ["done", "governance_proposal"],
  validation_produced: ["done"],
  done: ["notification_ack"],
};
```

`PreToolUse` enforces the state machine before mail tools run. `PostToolUse`
mirrors successful transitions. `Stop` checks that the agent is not abandoning a
claimed delivery.

Core enforcement examples:

| Tool | Rules |
| --- | --- |
| `wiki.mail.open` | active lease, visible delivery, nonterminal delivery, bodyless tool result, body delivered through injection |
| `wiki.mail.claim` | active lease, visible nonterminal delivery, conflicting claim denied, same-agent claim idempotent |
| `wiki.mail.mark(done)` | delivery claimed by current agent, evidence/reply/ref exists where required, terminal delivery cannot reopen |
| `wiki.notify.ack` | may not mutate delivery, allowed even if delivery is already claimed/done |
| `wiki.mail.send` | idempotency key, typed recipients, body hash, artifact refs for governed kinds |

### Stop And Compaction Guards

`Stop` is the completion seatbelt. If an agent is about to stop while it owns a
claimed nonterminal delivery, continue the turn with a concrete instruction:

```json
{
  "decision": "block",
  "reason": "You still have claimed delivery delivery_123. Before stopping, reply and mark it done, snooze it, reject it, or explicitly defer it with a reason."
}
```

Avoid infinite loops. After one or two stop-guard continuations, the supervisor
should create a `mail.warning.unclosed_claim` control event, optionally
auto-snooze under policy, mark the agent as `needs_supervisor`, and let the
turn stop.

Compaction guards preserve the same obligation:

- `PreCompact` writes `mail/active-context/<thread-id>.json` plus a
  `MailControlEvent`.
- `PostCompact` reinjects a small active-work reminder, never the full body
  unless `wiki.mail.open` authorizes a new injection.

## 1Context Mail Hook Kinds

These are the 1Context hook kinds that should exist above the Codex adapter.
They may map to Codex steering, polling, app-server notifications, or another
runtime's wakeup mechanism.

| Hook Kind | Trigger | Durable Truth | Adapter Action |
| --- | --- | --- | --- |
| `mail.delivery.created` | accepted message creates recipient delivery | delivery row | Create or refresh notification rows for matching non-retired agents. |
| `mail.notification.created` | delivery has routable agent target | notification row | Queue runtime wakeup. |
| `mail.notification.dispatch` | dispatcher attempts wakeup | notification attempt row | Steer active threads or resume/start inactive threads. |
| `mail.notification.failed` | wakeup transport fails | attempt row | Leave notification pending and schedule retry. |
| `mail.notification.acknowledged` | agent saw wakeup | notification state | Record wakeup handling only. |
| `mail.delivery.opened` | agent opens authorized body | delivery event | Audit body access and host injection. |
| `mail.delivery.claimed` | agent claims work | claim/delivery event | Suppress competing live notifications for same delivery. |
| `mail.delivery.marked` | agent marks read/done/archived/rejected | delivery event | Remove terminal deliveries from live notification pressure. |
| `mail.delivery.snoozed` | agent defers work | delivery event | Re-wake when due. |
| `agent.lease.expired` | live lease expires | agent directory | Stop live dispatch to that agent. |
| `agent.heartbeat` | agent renews lease | agent directory | Reconcile pending notifications. |
| `agent.retired` | agent exits permanently | agent directory | Stop live dispatch and reroute role/list work. |
| `mail.dead_lettered` | routing/retry/capacity fails terminally | dead-letter row | Make blocked work inspectable. |

Agents do not normally call hook dispatch directly. They call mail tools. Mail
tools create durable events. The supervisor/dispatcher turns those events into
hooks.

## Mail Correctness Rules

These rules decide whether the mailing system is correct.

1. **Mail body is durable truth.** Steering may carry an envelope/excerpt, but
   body access must go through `wiki.mail.open`; a Codex host delivers the
   authorized body into the thread with `thread/inject_items`.
2. **Every hook points to a delivery.** A wakeup without `delivery_id` and
   `notification_id` is not actionable enough.
3. **Any agent can message any routable address.** Agent-to-agent, role, list,
   page mailbox, and system routes all go through mail send/reply semantics.
4. **Notification ack is not delivery completion.** `wiki.notify.ack` only says
   the agent saw the wakeup.
5. **Claim suppresses competitors.** Once one live agent claims a shared
   delivery, competing pending notifications for that delivery are suppressed.
6. **Dispatch failure preserves work.** Failed steering leaves the notification
   pollable and the delivery unchanged.
7. **Leases gate agent self-service, not durable notification.** Stale agents
   cannot poll/claim as themselves, but the supervisor can still see their
   pending notification and try a resume/start wakeup.
8. **Heartbeat reconciles missed work.** If mail arrived while an agent was
   stale, heartbeat should make eligible pending notifications visible again.
9. **Terminal deliveries do not keep waking agents.** Done, archived, rejected,
   or dead-lettered work leaves durable audit state but not live pressure.
10. **Mail state does not trigger wiki publish.** Reading, claiming, marking,
    snoozing, acking, and dispatching hooks are not reader-content changes.
11. **Hooks are idempotent.** Repeated dispatch attempts for one notification
    use stable ids so agents and ledgers can de-duplicate.
12. **Soft steering is not safety.** Tool gates, approvals, sandbox, and host
    policy enforce safety.
13. **Every dispatch attempt is evidence.** Sent, failed, dry-run, suppressed,
    and retried hook attempts are durable enough to debug later.
14. **Control hooks leave evidence.** Hook decisions, app-server observations,
    injection receipts, and supervisor policy choices go into
    `mail/control-events.jsonl`.
15. **Hook control does not mutate message truth directly.** Hooks may enqueue,
    block, mirror, or add context; message and delivery state changes still
    happen through mail APIs.

## Agent Mail Tool Risk Classes

The public agent API should stay small, but internally the gateway should know
which mail actions are read-like, state-mutating, or administrative. That lets
Codex approvals and hooks be strict without making normal inbox use painful.

| Class | Example Operations | Approval Posture |
| --- | --- | --- |
| inspect | `wiki.agent.identity`, `wiki.agent.inbox`, `wiki.mail.open` | No host approval; enforce mailbox authorization in mail core. |
| acknowledge | `wiki.notify.ack` | No host approval; only mutates notification evidence. |
| claim/mark | `wiki.mail.claim`, `wiki.mail.mark`, `wiki.mail.snooze` | No host approval for own deliveries; mail core checks rights and leases. |
| create | `wiki.mail.send`, `wiki.mail.reply` | No host approval for routable mail; rate-limit and audit. |
| reroute | delegate role/list delivery, suppress competing wakeups | Supervisor-owned or governed role policy. |
| administer | register/retire agents, dead-letter, edit routing rules | Host/supervisor only; not normal agent tool use. |
| execute | shell, file mutation, deployment, network access caused by mail | Normal Codex tool approval/sandbox path, never mail approval. |

The key distinction: `wiki.mail.claim` can claim responsibility for a message,
but it cannot approve filesystem writes, network access, deploys, or destructive
commands. Those remain Codex/tool policy decisions.

## Hook Use Matrix For Mail

| Need | Preferred Mechanism | Reason |
| --- | --- | --- |
| Wake an active Codex agent for new mail | `turn/steer` via notification dispatcher | Immediate and tied to current active turn. |
| Wake an inactive but resumable agent | supervisor reads dispatch queue, resumes/starts thread, then `turn/start` or steering | Durable notification already exists; push transport catches up. |
| Deliver an opened mail body | `wiki.mail.open`, then host `thread/inject_items` | Open enforces mailbox authorization; injection makes the body model-visible. |
| Add memory/context before work starts | `SessionStart` or `thread/inject_items` | Context, not message truth. |
| Stop unsafe mail-adjacent command | `PreToolUse` or `PermissionRequest` | Harder than soft steering. |
| Require claimed mail cleanup before final answer | `Stop` | Continuation gate. |
| Require spawned worker to mark/delegate mail | `SubagentStop` | Continuation gate for worker. |
| Record complete runtime evidence | app-server event stream plus 1Context ledgers | Final answer text is not enough. |
| Prompt user for approval | app-server approval flow | Human/policy boundary. |
| Talk to another agent | `wiki.mail.send` / `wiki.mail.reply` | Durable, routable, auditable. |

## Supervisor Responsibilities

The autonomous supervisor owns:

- watching mail ledgers and notification outbox
- selecting eligible live recipients from the agent directory
- dispatching runtime hooks
- recording attempts
- retrying transient failures with backoff
- suppressing competing wakeups after claim
- reconciling notifications on heartbeat
- expiring leases
- retiring agents
- dead-lettering blocked work
- observing Codex event streams for errors and completion

The supervisor should not:

- invent mail body text
- mark delivery done on behalf of an agent unless a separate governed policy
  explicitly permits it
- publish the wiki merely because mail hooks ran
- treat a final assistant message as delivery completion without the mail ledger
  transition
