Apple Signing, Developer Certificates, and Provisioning

How Apple went from Mac code signatures to a full release trust system: certificates, private keys, App IDs, entitlements, provisioning profiles, Gatekeeper, notarization, TestFlight, App Store distribution, and CI.

The Mental Model

Apple signing is not one thing. It is a chain of identity, permission, integrity, policy, and distribution. Most confusion comes from treating certificates and provisioning profiles as interchangeable. They are not.

Certificate

Answers: who signed this? A signing certificate is issued by Apple to a person or team. Signing requires the matching private key, usually stored in Keychain or exported as a password-protected .p12.

Provisioning profile

Answers: is this app allowed to run this way? A profile binds Team ID, App ID, certificate, entitlements, devices where needed, and an expiration window.

Code signature

Answers: has this exact bundle changed? The signature seals the executable, resources, Info.plist, entitlements, and signing requirements. Modify the app after signing and validation fails.

Practical rule: A downloaded .cer is not enough. If the Mac or CI runner does not have the matching private key, Xcode may show the certificate, but it cannot sign with it.

Historical Arc

Apple started with a relatively open Mac model and progressively added formal identity, distribution, launch policy, and malware scanning. On iPhone and iPad, Apple took a stricter path from the beginning: centralized distribution, mandatory code signing, App Review, and sandboxing. The systems now share a vocabulary, but their default policies are still different.

2007
Modern Mac signing documentation appears. Apple had already been building the machinery for signed code in Mac OS X. Leopard-era documentation formalized code signatures, requirements, and verification concepts.
2008
iPhone SDK and App Store. Native iPhone apps arrive with a developer program, device testing, signing certificates, and App Store distribution.
2011
Mac App Store. The Mac gains a store-distribution channel where apps are reviewed, distributed, and ultimately signed for store delivery.
2012
Gatekeeper and Developer ID. OS X Mountain Lion introduces Gatekeeper, allowing users to prefer Mac App Store apps and apps signed by identified developers with Developer ID.
2013-2014
Mavericks-era v2 signatures. Apple tightens bundle sealing rules. Resource rules that let developers exclude files from the seal become obsolete.
2017
Developer ID profile lifetime policy. Developer ID provisioning profiles generated after February 22, 2017 are valid for 18 years, independent of the Developer ID certificate expiration.
2018-2019
Notarization becomes central for Mac distribution. Developer ID-signed software distributed outside the Mac App Store moves toward mandatory notarization under default Gatekeeper settings.
2021
DER entitlements for newer OS checks. iOS 15, iPadOS 15, tvOS 15, and watchOS 8 enforce newer signature formats for affected apps with entitlements.
2023
notarytool replaces the old notarization path. As of November 1, 2023, Apple no longer accepts notarization uploads from altool or Xcode 13 and earlier.
2024
EU alternative iOS distribution. iOS 17.4 adds DMA-related alternative distribution options in the EU, with iOS app notarization, marketplace authorization, install disclosures, and extra malware protections.

How the Technical Pieces Fit

1. Signing identities

A signing identity is the useful thing: certificate plus private key. The certificate is public and comes from Apple. The private key is generated on your Mac when you create a certificate signing request, or managed by Xcode/cloud systems. The private key is what actually signs. Without it, the certificate is only an identity document.

2. App IDs and bundle IDs

The bundle ID is the app name in Apple policy space, usually com.company.product. The App ID in the developer account connects that bundle ID to capabilities such as Push Notifications, iCloud, App Groups, Associated Domains, Apple Pay, Sign in with Apple, or HealthKit. Wildcard App IDs are convenient for simple development, but explicit App IDs are required for many real capabilities and for App Store Connect distribution.

3. Entitlements

Entitlements are key-value claims embedded into the code signature. They are not comments and they are not merely project settings. When you turn on a capability in Xcode, Xcode typically updates an .entitlements plist and also updates or requests signing assets so the final app signature and profile agree. 

<key>com.apple.security.app-sandbox</key>
<true/>
<key>com.apple.security.network.client</key>
<true/>

The operating system uses these signed entitlements to decide what privileged behaviors are permitted. If your app claims an entitlement that your provisioning profile or developer account does not authorize, signing, upload, install, or launch can fail.

4. Provisioning profiles

Provisioning profiles are Apple-signed authorization documents. They are commonly decoded with security cms -D because their payload is a property list wrapped in a CMS signature.

5. Code signatures inside bundles

For app bundles, signing creates a seal over the executable, resources, Info.plist, nested code, requirements, and entitlements. macOS app bundles store resource seal data under paths such as Contents/_CodeSignature/CodeResources. iOS app bundles commonly contain an embedded provisioning profile at embedded.mobileprovision. 

MyApp.app/
  Info.plist
  MyApp
  embedded.mobileprovision
  _CodeSignature/
    CodeResources
  Frameworks/
    SomeFramework.framework/

Nested code must be signed before the outer app is signed. That includes frameworks, extensions, helper tools, login items, plug-ins, and sometimes bundled command-line tools.

File Extensions You Will Actually See

These are the mundane files that make Apple signing feel opaque. Treat this as a map from file name to responsibility.

.certSigningRequest CSR created from Keychain Access or command line. Upload this to Apple to request a certificate.
.cer Downloaded public certificate from Apple. Install by double-clicking. Not useful for signing unless the matching private key is present.
.p12 / .pfx Password-protected export containing certificate plus private key. Used to move a signing identity to another Mac or CI.
.mobileprovision iOS-family provisioning profile file. Downloaded from Apple or managed by Xcode.
.provisionprofile macOS provisioning profile extension, especially for Developer ID or Mac profiles with advanced capabilities.
.entitlements Property list describing requested capabilities. Final entitlements are embedded into the code signature.
.app Application bundle. It is a directory presented as a single app in Finder.
.ipa iOS app archive for device/App Store distribution. Xcode exports this from an .xcarchive.
.xcarchive Xcode archive bundle containing the built app, dSYMs, signing metadata, and export inputs.
.plist Property list. Common examples: Info.plist, ExportOptions.plist, DistributionSummary.plist.
.pkg macOS flat installer package. Sign with a Developer ID Installer cert for direct distribution.
.dmg macOS disk image. Often signed and notarized for direct-download apps.
.zip Can carry a Mac app for notarization upload. Stapling applies to the contained app, pkg, or dmg, not a plain zip itself.
.dSYM Debug symbols. Not signing assets, but usually archived and uploaded for crash symbolication.
.p8 App Store Connect API key private key, used to sign API JWTs. This is not a code-signing certificate.

The Website Mechanics: What to Click

The Apple Developer website is not organized around your task. It is organized around asset types. When you feel lost, go back to this sequence: Identifier -> Capability -> Certificate -> Device -> Profile.

Roles matter. Account Holder and Admin can create many distribution assets. Regular team members may be blocked. If buttons are missing, check your role before debugging Xcode.

Find the right place

  1. Go to developer.apple.com/account/resources.
  2. Open Certificates, Identifiers & Profiles.
  3. Use the left sidebar: Certificates, Identifiers, Devices, Profiles.
  4. If you belong to several teams, switch to the correct team first. A wrong team creates assets that will never match your app.

Create a certificate manually

Create the CSR on the Mac that should own the private key

Open Keychain Access at /Applications/Utilities. Choose Keychain Access > Certificate Assistant > Request a Certificate from a Certificate Authority. Enter your email and a recognizable common name, leave CA Email empty, choose Saved to disk, and save the .certSigningRequest.

Choose the certificate type on Apple's site

In Certificates, click +. Pick the type: Apple Development for device development, Apple Distribution for TestFlight/App Store/ad hoc, Developer ID Application for direct Mac apps, or Developer ID Installer for direct Mac installer packages.

Upload the CSR and download the certificate

Upload the .certSigningRequest. Apple returns a .cer. Download it. Double-click it on the same Mac that created the CSR. It should appear in Keychain Access under My Certificates with a private-key disclosure triangle.

Confirm the private key exists

In Keychain Access, the certificate should expand to show a private key. If it does not, you installed only the public certificate. Either find the Mac that generated the CSR or create a new certificate from this Mac.

Export a .p12 for another Mac or CI

  1. Open Xcode > Settings > Accounts.
  2. Select your Apple Account and team, then click Manage Certificates.
  3. Control-click the certificate and choose Export Certificate.
  4. Save it as a .p12 with a strong password.
  5. Store the .p12 and password in your team secret manager. Do not commit them.

Create or update an App ID

  1. Open Identifiers, click +, choose App IDs, then choose App.
  2. Use an explicit Bundle ID like com.example.product for production apps.
  3. Turn on capabilities here or from Xcode's Signing & Capabilities pane.
  4. If you add a capability later, regenerate or refresh profiles so the entitlement appears in them.

Register test devices

  1. Open Devices, click +.
  2. Add the device name and UDID. Xcode can also register devices automatically when automatic signing is enabled.
  3. Remember: development and ad hoc profiles need registered devices. App Store/TestFlight profiles do not use a device list in the same way.

Create a provisioning profile

Development profile

Use for running on your own devices while developing. It includes development certificate(s), the App ID, entitlements, and selected devices.

Ad hoc profile

Use for distributing an .ipa to registered devices outside TestFlight. It includes a distribution certificate and selected devices.

App Store Connect profile

Use for App Store/TestFlight upload when signing manually. It uses an explicit App ID and one distribution certificate.

Developer ID profile

Use for some direct-distributed Mac apps that need advanced capabilities such as CloudKit or push notifications.

To download a profile, open Profiles, select the profile, and click Download. Apple documents downloaded profile extensions as .mobileprovision or .provisionprofile.

If the profile looks stale or wrong
  1. Check the App ID capabilities first.
  2. Edit or regenerate the profile after capability/device/certificate changes.
  3. In Xcode, download manual profiles from Accounts settings.
  4. If automatic signing is stuck, remove stale files from ~/Library/MobileDevice/Provisioning Profiles/ and rebuild.

Xcode Workflow

Automatic signing

For most solo and small-team development, automatic signing is the right default. Add your Apple ID in Xcode, assign a team to each target, turn on capabilities, and let Xcode create development certificates, App IDs, devices, and profiles as needed.

Use automatic signing when: you are building a normal app, your team roles allow it, CI can use Xcode Cloud or cloud-managed certificates, and you do not need exact control over which certificate/profile signs each target.

Manual signing

Use manual signing when you need reproducible CI builds, strict separation of development/release identities, client accounts, multiple bundle IDs, or extension-heavy projects where each target needs a different profile.

Setting What it must match Common failure
PRODUCT_BUNDLE_IDENTIFIER App ID / provisioning profile Profile does not include the app identifier.
DEVELOPMENT_TEAM Team ID in cert/profile Assets created under wrong developer team.
CODE_SIGN_STYLE Automatic or Manual workflow CI expects manual profiles but Xcode tries to auto-manage.
CODE_SIGN_IDENTITY Certificate type Using development cert for distribution or Developer ID.
PROVISIONING_PROFILE_SPECIFIER Profile name or UUID Wrong target gets wrong profile, especially extensions.

Archive and export

Xcode's release unit is usually an .xcarchive. From that archive, Xcode can upload to App Store Connect or export local files. Apple documents that the export folder can include ExportOptions.plist, DistributionSummary.plist, Packaging.log, and an installer file such as an .ipa or .pkg. 

xcodebuild archive \
  -scheme MyApp \
  -configuration Release \
  -archivePath build/MyApp.xcarchive

xcodebuild -exportArchive \
  -archivePath build/MyApp.xcarchive \
  -exportOptionsPlist ExportOptions.plist \
  -exportPath build/export

Release Pipelines

Different distribution channels use the same primitives but different policies. The diagram below shows the common professional flows.

iOS, iPadOS, tvOS, watchOS, visionOS

These platforms require Apple-issued signatures for executable code. Development builds run on registered devices under development profiles. Ad hoc builds run on registered devices under ad hoc profiles. TestFlight and App Store builds are uploaded to App Store Connect, processed, and distributed through Apple systems.

macOS App Store

Mac App Store apps use Mac App Store distribution signing assets and App Store Connect. Store delivery is distinct from direct Developer ID distribution.

macOS outside the Mac App Store

Direct Mac distribution usually means Developer ID Application for the app, Developer ID Installer for a flat .pkg, hardened runtime, secure timestamping, notarization with notarytool, and stapling with stapler. 

codesign --force --options runtime --timestamp \
  --sign "Developer ID Application: Example Inc. (TEAMID)" \
  MyApp.app

ditto -c -k --keepParent MyApp.app MyApp.zip

xcrun notarytool submit MyApp.zip \
  --keychain-profile "notary-profile" \
  --wait

xcrun stapler staple MyApp.app
spctl -a -vvv -t exec MyApp.app

CI and Team Operation

Professional teams try to make signing boring. That means naming assets clearly, limiting who can create/revoke distribution certificates, storing secrets in a proper secret manager, and separating development, beta, production, and direct Mac release workflows.

Typical non-Xcode-Cloud CI setup

  1. Store the .p12 in CI secrets or a signing asset repository with encryption.
  2. Store the .p12 password separately.
  3. Store provisioning profiles as secret files or fetch them with a controlled tool.
  4. At job start, create a temporary keychain, import the .p12, unlock the keychain, and install profiles.
  5. Run tests, archive, export, then upload with Xcode, Transporter, App Store Connect workflows, or platform tooling.
  6. Delete the temporary keychain after the job.
security create-keychain -p "$KEYCHAIN_PASSWORD" build.keychain
security import signing.p12 -k build.keychain -P "$P12_PASSWORD" -T /usr/bin/codesign
mkdir -p "$HOME/Library/MobileDevice/Provisioning Profiles"
cp profiles/*.mobileprovision "$HOME/Library/MobileDevice/Provisioning Profiles/"

Xcode Cloud

Xcode Cloud can reduce local signing pain because Apple can use cloud-managed certificates and workflows tied to your Apple Developer team. It is often the cleanest option for standard App Store/TestFlight pipelines. You still need to understand bundle IDs, capabilities, entitlements, and team roles because Xcode Cloud cannot fix a logically wrong App ID or missing entitlement.

Rotation and incident handling

Event What to do Risk
Development cert expires Create a new development cert/profile or let Xcode refresh automatic signing. Developers cannot install debug builds until refreshed.
Distribution cert expires Create a new distribution cert, regenerate profiles, update CI secrets. Uploads and ad hoc/in-house distribution can break.
Private key lost Export .p12 from original Mac or create/revoke as appropriate. A visible certificate cannot sign without its private key.
Private key compromised Revoke affected certificate, create new cert, regenerate profiles, audit shipped software. Revocation can affect installs/launches depending on channel.
Capability changed Regenerate profile and verify entitlements in the final signed app. App may upload but feature fails, or upload/install fails.

Debugging Signing Problems

Inspection commands

# List usable code-signing identities
security find-identity -v -p codesigning

# Decode a provisioning profile
security cms -D -i MyProfile.mobileprovision > profile.plist

# Show signature metadata
codesign -dv --verbose=4 MyApp.app

# Show embedded entitlements
codesign -d --entitlements :- MyApp.app

# Verify app signature deeply and strictly
codesign --verify --deep --strict --verbose=2 MyApp.app

# Assess Gatekeeper policy for a Mac app
spctl -a -vvv -t exec MyApp.app

Common errors translated

Error shape Likely meaning First checks
"Missing private key" You installed a .cer but not the private key. Check Keychain > My Certificates. Export/import .p12 or recreate cert from this Mac.
"Profile doesn't include signing certificate" The selected profile was generated for a different certificate. Edit/regenerate profile with the active certificate; refresh Xcode profiles.
"Entitlement not supported" The app signature claims a right not authorized by the profile/account. Check App ID capabilities, profile entitlements, and final app entitlements.
"No matching provisioning profiles" Bundle ID, team, device, cert type, or profile type does not match. Compare PRODUCT_BUNDLE_IDENTIFIER, Team ID, device UDID, and distribution method.
Gatekeeper says app cannot be checked Mac app is unsigned, signed with wrong identity, not notarized, or altered after notarization. Run codesign, spctl, and stapler validate.
A reliable manual-signing checklist
  1. Confirm the Apple Developer team is correct.
  2. Confirm the bundle ID matches the App ID exactly.
  3. Confirm the certificate type matches the distribution method.
  4. Confirm the profile includes that certificate.
  5. Confirm the profile includes the device for development/ad hoc.
  6. Confirm the profile includes the required entitlements.
  7. Confirm every nested target has its own matching profile.
  8. Archive cleanly, inspect final entitlements, then upload/export.
